  <action>
    **Investigation (per SAVE-02 locked decision):**
    Trace the MainScreenModel init state machine (lines 305-397 of MainScreenModel.kt) to identify why data loading fails in the secondary Activity context. The init block uses `screenModelScope.launch` for three things:
    1. Coroutine A (line 314): collects `servers` flow, sets `_selectedServer`
    2. Coroutine B (line 326): runs the init state machine (ResolvingFilter -> WaitingForServer -> LoadingInitialPage -> Ready)
    3. Coroutine C (line 364): collects `bookmarkChangedEvents`

    **Key insight from research:** `MainScreenModel` is Koin `single {}` (AppModule.kt line 107). When a new Voyager Navigator is created in BookmarkSavingActivity, Voyager's `koinScreenModel` may either:
    - (a) Return the existing singleton with a potentially cancelled `screenModelScope`, OR
    - (b) The Koin `single {}` means only ONE instance ever exists, but Voyager's ScreenModelStore lifecycle may have already disposed it

    **Diagnosis strategy:**
    1. Write the regression test FIRST (RED phase) that creates a MainScreenModel with the same MockK setup as QuickFilterCountsTest, stubs `getBookmarksPaged` to return bookmark data, then asserts `_accumulatedBookmarks` is non-empty after `advanceUntilIdle()`
    2. Run the test -- if it passes, the init state machine works fine in isolation. The bug is then in Voyager lifecycle management (screenModelScope cancellation) rather than in the init logic itself.
    3. If the test fails, the bug is in the init logic and the fix goes in MainScreenModel.kt

    **Likely fix directions:**
    - If the issue is Voyager scope cancellation: The Koin `single {}` creates ONE instance, but when the first Navigator disposes, `ScreenModel.onDispose()` is called and `screenModelScope` is cancelled. A second Navigator calling `koinScreenModel` gets the SAME instance from Koin singleton, but its `screenModelScope` is dead. Fix: either change from `single {}` to `factory {}` in AppModule.kt (so each Navigator gets a fresh instance), OR add a re-initialization mechanism in MainScreenModel that detects a cancelled scope and re-runs init.
    - If the issue is init flow timing: Fix the specific flow that doesn't emit (add logging, ensure DataStore flows emit, etc.)

    **After diagnosis, implement the fix and make the test GREEN.**

    Use the QuickFilterCountsTest pattern for test setup: Robolectric runner, StandardTestDispatcher, relaxed MockK mocks, explicit stubs for all settings flows, MutableSharedFlow for event flows.
